# 核准噪音量測結果（2026-10-15）

**這份報告只產生證據，不改分析器，也不建議放寬任何工具**；放寬與否是之後 Roy 逐個決定的事。
方法在看資料前寫定（`mapping.md`、`standard.md`），並經兩輪小o 事前審查修訂；本報告是第三次標記（前兩次作廢，見最後一節）。

## 一句話

在 Roy 最近 30 天的 Claude Code 工作裡，現行分析器對 **68.4%** 的可對應工具呼叫要求核准；其中被問到的呼叫有 **28.5% 到 73.3%**
被標記者認為不必問（區間來自「無法判定」佔 44.9%）。**噪音的量主要在 Bash，而 Bash 在這種去識別下有一半無法判定**，所以 Bash 的噪音
只能給區間，不能給點估計。有幾類是明確、量小的噪音（沒帶路徑的 grep／glob、任務清單工具）。

## 母體與覆蓋率

- 來源：本機 Claude Code 對話，最近 30 天（以每筆紀錄自己的時間戳篩選），已以 `tool_use` id 去重。母體會隨時間與這個 session 本身增長。
- 讀取 976 個逐字稿檔，**其中 67 個是子代理（subagent）的巢狀逐字稿**（用檔案系統另行計數核對過：路徑含 `subagents` 的 `.jsonl` 共 67 個）；第一、二次標記漏掉了它們（掃描只看第一層），第三次補上。若逐字稿有被清除或輪替，更早的呼叫不在母體內（保留期見記憶中的 `cleanupPeriodDays` 設定，未在此核對每一天的覆蓋）。
- 工具呼叫 **19,103** 筆；可對應並送進真分析器 **17,867** 筆（含 MCP 935 筆）；**無對應 1,233 筆**（`WebSearch`、`WebFetch`、`Skill`、`ToolSearch` 等 Claude Code 自己的工具）；格式不全 3 筆；相對路徑無法解析 0 筆；解析失敗 0 行。
- **結論只限定於這 17,867 筆**，不外推到整個工作負載，也不外推到 OpenHands agent 實際會做的事。

## 解讀（每一句都限定在上表與下列限度內）

1. **最大的量在 Bash，但 Bash 最看不清。** 抽到的 90 筆裡，必要 21、不必要 19、無法判定 50。無法判定的主因是指令詞的作用被隱去
   （其他 16、直譯器跑腳本 15、指令內容有隱藏部分 9，其餘為組合或資訊不足）。依層權重加權後，被問到的 Bash 裡不必要的比例約 **28% 到 77%**
   （下界把無法判定當必要、上界當不必要），寬到不能說一個數字。要把 Bash 看清，需要比這種去識別更多的資訊，也就是**讓有權看原始指令的人（Roy 自己，或你同意的方式）標記一小批**。
2. **檔案類被問到的呼叫，過半必要**（44 筆中 28 筆）：這 28 筆都是寫入或建立工作區外的檔案（`str_replace` 13、`create` 15）。不必要的 16 筆全是「讀取工作區外的非祕密檔案」（`view`），
   這是 `standard.md` 的一個**有意選擇**（更嚴的團隊會不同意）。
3. **明確、量小的噪音**：沒帶路徑的 `grep`／`glob` 與 `task_tracker`，抽到的 59 筆全部被標為不必要。這三類加起來只有 227 筆（1.3%），
   所以放寬它們不會明顯降低整體核准量；但它們看起來是分析器規則的副作用（`path` 欄位缺漏、`command` 欄位名稱），而不是風險判斷。
4. **MCP 看不出來**：50 / 50 無法判定（只有名稱，沒有參數與讀寫性質）。這是 O3（MCP 工具准入）要處理的問題，不是這份資料能回答的；
   MCP 全部算「無法判定」也會把 A 的上界撐高（MCP 占被問到呼叫的 935 / 12,221，約 7.7%）。
5. **沒被問到的動作裡，沒有標記者認為必要的**（0 / 70，都是工作區內的檔案動作與搜尋，含編輯與建立）。這個樣本小，只能說「沒有看到漏問的證據」，不能說「沒有漏問」。
6. **探索性的候選（不是結論）**：只由特徵推出的一條簡單規則——Bash 動作的作用類別只含讀取、版本控制唯讀、測試／建置工具，且沒有隱藏部分、
   沒有重導向、沒有區外路徑、沒有送出資料、沒有祕密路徑、沒有網址、沒有 pipe 進 shell——在全母體命中 **896 / 9,143（9.8%）**。
   它是**看過標記之後才提出的**；條件實作在 `report.py` 的 `candidate_rule_hits`（有測試，每個條件單獨拿掉都會讓測試失敗），重跑 `report.py` 會印出同一個命中數；抽樣裡命中的只有 6 筆，6 / 6 被標為不必要。6 筆只能支持「沒看到反例」，不能支持「很準」。
   若要認真考慮它，需要更多樣本與你自己的判斷。（先前版本寫 892 / 9,087，母體與規則實作都和現在不同，不要拿來對。）

## 限度（請一併讀）

- 標記者是模型（小o），與小c 是不同廠牌但仍是模型；標準是**一個**合理的標準，不是唯一的。
- 標記者每筆獨立、看不到前後文與使用者意圖，這會讓「必要／不必要」的邊界偏向保守或無法判定；我沒有量化這個偏差。
- 這是 Claude Code 的使用，不是 OpenHands agent 的行為，也偏向 Roy 本人的研究型工作與習慣。
- 母體取決於逐字稿保留與輪替：有被清掉的更早對話不在內；子代理逐字稿一開始被漏掉，第三次才補。
- `cwd` 為家目錄或更高層的對話（`broad`）裡，「在工作區內」幾乎涵蓋整顆磁碟，**檔案類動作的免核准比例被高估**；沒有外生的更嚴格定義可用。
- 沒有「檔案是否被版本控制追蹤」的資訊，所以把「可由版本控制回復」當作對工作區內編輯的一般性假設。
- 區間是近似法；各層樣本小（最大層 50 筆）；樣本不足 15 筆的層全取，不算區間。
- 去識別讓部分 Bash 無法判定，並以區間呈現；Bash 解析不是完整的 shell 解析（見 `replay.py` 與其測試的涵蓋範圍）。
- 這份資料不涉及：這些必要動作是否該用別的機制（沙盒、網路政策）擋，不評論。

## 方法的過程（為了誠實）

- 方法文件在看資料前寫定，經小o 兩輪事前審查（抓到：W2 工作區定義有內生性並已刪除、相對路徑沒依 cwd 轉絕對、估計量與抽樣權重沒寫清楚、
  Bash 去識別資訊不足、工具名稱沒去識別、取樣上限與權重不相容、MCP 不該預先排除等）。
- **第一次標記作廢**：我的 Bash 特徵有 bug（一段指令只要沒新增任何作用類別，就被誤判為「無法分類」，
  所以 `cd x && ls` 這種唯讀指令也被標成未知）。已修正、加回歸測試（把舊 bug 放回去測試會失敗），整個流程重跑。第一次的區間是 A 12.6% 到 69.4%、無法判定 56.7%。
- **第二次標記也被取代**：小o 事後審查指出三件事——bootstrap 把不同層的對話混在一個池裡抽（已改為每層內重抽，整層採全取的不重抽）、
  掃描漏掉子代理的巢狀逐字稿（67 檔）、報告文字把「沒被問到」樣本寫成 90 筆且說成只含讀（實為 70 筆、含編輯建立）。
  第二次的結果是 A 25.2% 到 65.0%、無法判定 39.8%；現在是 28.5% 到 73.3%、44.9%。
- 標準 `standard.md` 在三輪都在看資料前寫定，沒有因結果修改。
